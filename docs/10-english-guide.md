# 10. 영어 학습 기능 가이드 (English Guide)

> **이 문서의 독자**: 이 기능을 실제로 구현할 사람.
> **성격**: 방향과 근거. 여기 없는 것(프롬프트 문구·테이블 정의·API 시그니처)은
> 구현자가 사용자와 먼저 논의하고 정하는 것으로 남겨 두었습니다.

---

## 1. 이 문서의 목적

현재 `/english`는 학습 기능이라기보다 **"LLM 채팅에 JSON 스키마를 붙인 것"**에 가깝습니다.
한 번 테스트를 하고 실제 사용은 하지 않았습니다.

그래서 지금이 설계 판단이 덜 굳어 있는 시점입니다. 다음 문서(`08-decisions.md`)가
쌓아 온 원칙을 이 기능에도 그대로 적용합니다.

- 코드를 고치기 **전에** 결정을 남긴다
- 무엇을 골랐는지보다 **왜 다른 쪽을 버렸는지**를 남긴다
- 계측 전에는 "이득이 있다"고 단정하지 않는다

---

## 2. 목표

### 실제 목표 (사용자 진술)

- **수준**: 원어민과의 초중생 수준 대화는 가능하다 (CEFR로는 대략 B1)
- **바라려는 것**: 그 이상으로 **유창하게 말하고 싶다**
- **쓰임새**: 해외 고객과의 비즈니스 대화가 생길 수 있음

### 그래서 이 기능이 해야 하는 일

1. **속도와 리듬** — 짧고 정확한 문장보다, 멈추지 않고 이어가는 능력
2. **연결과 완충** — 진짜 원어민 대화가 끊기지 않게 하는 요소들
3. **상황 대응** — 특히 비즈니스 대면에서 필요한 표현과 리듬
4. **자기 실수 복습** — 내가 실제로 못하는 것을 골라서 다시

### 비목표 (이 기능이 하지 않는 것)

- 문법 수업. 수준별 문법 커리큘럼은 넣지 않습니다
- 시험·어휘시험 대비. 채점·등급 산출 없음
- CEFR 레벨 선택 UI. 지금 수준은 이미 알고 있고, 선택지가 되돌 제약이 됩니다
- "정답 문장"을 맞히는 훈련. 발음을 맞히게 만드는 것이 아닙니다

---

## 3. 왜 스킬 분해를 하지 않는가

가장 먼저 정해야 할 구조적 결정입니다. 여기서 갈리는 갈림길이 나머지를 다 결정합니다.

**거절한 방향**: 스킬 단위 분해 (어휘 / 문법 / 회화를 각각 세션으로 나눠 반복 스케줄로 관리)

이 방향이 논리적으로는 가장 잘 정렬된 설계처럼 보입니다. 하지만 목표와 어긋납니다.

| 프리 토킹에 필요한 것 | 스킬 분해가 주는 것 |
|---|---|
| 대화의 흐름을 끊지 않는 능력 | 대화의 흐름을 매번 같은 형태로 절단 |
| "A가 B가 되냐"는情境 판단 | 상황별 문법 항목 |
| 같은 표현을 다른 날 다시 마주침 | 세션마다 새로 생성된 표현 |

문법과 어휘는 **없애는 게 아니라 "쌓인 것만" 다룹니다.** 5절에서 나옵니다.

---

## 4. 핵심 원리: 피드백을 세션 말미로 미룬다

이 문서에서 가장 중요한 한 항목입니다. 현재 프롬프트는
"사용자가 틀린 문장을 썼다면 한국어로 왜 틀렸는지 알려주고 올바른 버전을 제시하세요"로 되어 있습니다.

대화 중에 교정을 끼워 넣으면 학습자는 두 가지를 동시에 하게 됩니다.
** communicative intent를 유지하는 일**과 **형태를 고치는 일**입니다.
결과적으로 말하기를 멈추고 교정 위주 대화가 됩니다. 유창함을 만드는 것이 아니라
정확성 수업이 됩니다.

따라서:

> **대화 중에는 이해를 방해하는 오류만 즉각 교정한다. 나머지는 전부 세션 말미로 미룬다.**

이건 "교정을 하지 말라"는 뜻이 아닙니다. **위치를 옮기는 것**입니다.
교정은 정확하게 하되, 대화가 끝난 뒤에 합니다.

구현에 미칠 영향 (형태는 구현자가 정함):

- 턴당 즉각 교정 **예산**을 두는 방식이 필요합니다. 프롬프트에 부탁만 하지 말고 개수로 제한
- 기본값은 보수적으로 시작 (교정을 거의 하지 않는 쪽)
- 교정이 필요 없는 게 맞다고 **느끼는 것**도 성공 조건입니다
- 한 턴에 예문·번역·피드백이 한꺼번에 나오면 대화 흐름이 끊기므로, 말미에는 스크롤 가능한 요약 형태로

근거: 이 순서 선택이 "교정 정확도"보다 "유창함"을 더 크게 좌우한다.
반대 위치는 대화 중 학습자의 발화량을 줄이는 방향으로만 작동합니다.

## 5. 학습은 "맞힌 것"이 아니라 "틀렸던 것"으로 쌓는다

대화가 쌓이는 것만으로는 다음 세션이 좋아지지 않습니다. 다음 세션이 달라지려면
**무엇이 남는지**가 있어야 합니다.

### 남길 것 (구체적 형태는 구현자 협의)

**a. 자기 오류 기록**
말미로 미룬 교정이 여기 쌓입니다. 한 건당 원문 / 수정 / 사유.
이 목록이 쌓이면 **문법 학습이 저절로 생깁니다.** 모든 문법을 다룬다 대신
내가 실제로 자주 틀리는 것만 반복됩니다.

- 현재 대화에서만 유효한 것과 세션을 넘어 이어지는 것을 구분
- 사유를 자유 텍스트로 두지 말고, **재사용 가능한 분류**를 두는 것을 고려
  (과거형, 관사, 전치사, 어순, 접속 …) — 이 분류가 "지금 무엇을 연습할지"를 정하는 근거가 됩니다
- 같은 분류가 계속 쌓이면 그 항목이 다음 세션의 주제가 됩니다

**b. 배운 표현 (chunk)**
**단어가 아니라 구 단위로** 남깁니다.

- `"I was wondering if ..."`, `"let me get back to you on that"`,
  `"to give you a bit of background"` 같은 것들
- 네이티브도 사전적 어휘보다 이런 구슬을 씁니다. 단어를 외워도 조합을 못 하면 대화되지 않습니다
- 실제 유창성을 가장 빨리 올리는 지름길은 **말할 수 있는 구슬의 개수**입니다

**c. 주제와 상황**
무슨 이야기를 했는지. 같은 주제로 다시 진입할 수 있어야 합니다.
비즈니스 고객 대화라는 목표가 있으므로, 상황 목록이 이 축에서 결정됩니다.

### 반복(review)에 대한 원칙, 그리고 아직 안 하는 것

- **원칙**: 이번 세션에서 다룬 표현은 다음 세션에서 먼저 다시 등장해야 합니다.
  새 표현만 계속 늘면 유창함이 안 느는 이유가 됩니다
- **아직 정하지 않은 것**: 반복 간격을 어떤 기준으로 잡을지.
  오류 빈도? 경과 시간? 마지막 실패 시점? 일단 기록만 쌓아 두고 나중에 정해도 됩니다.
  지금 정하려 들면 계측 없이 추측을 문서화하게 됩니다

## 6. 발음

프리 토킹 목표에서 발음은 선택이 아닙니다. 못 들리는 말은 대화되지 않습니다.

### 접근 방향

- **최소대조 쌍(minimal pair) 반복**: 학습자가 실제로 오독하는 소리만 반복해서 다룹니다.
  한국어 화자에게 자주 어려운 `/θ/` `/ð/`, `L/R`, 자음군, `-ed` 끝 소리 같은 것
- **섀도잉(shadowing)**: 예문을 통째로 따라 말하기. 문법 소모 없이 입 모양·리듬을 익힌다
  - 이건 **연습에 실패할 여지가 적다**는 점에서 좋습니다. 발음 검사 없이도 됩니다
- 예문 하나에 음성 버튼이 붙는 현재 방식은 그대로 쓰되, 반복의 대상이 되어야 합니다

### 구현 시 주의

- 음성 합성은 **기계 목소리**입니다. 원어민의 속도·억양을 가르쳐 주지 못합니다.
  그러니 "듣기"를 성취로 표시하지 마세요
- 말하기 연습(내가 말하는 것)이 듣기보다 약합니다. 이건 별개 문제로 남겨 두고
  지금은 들기 쪽만이라도 제대로 잡습니다
- **음성 입력(내 목소리로 말하기)은 목표와 거리가 멀어 보이지만 실제로는 중심 기능입니다.**
  타이핑으로 답하는 구조는 "말하기"가 아니기 때문입니다.
  - 기존 보류 사유(인식 오류 → 학습자가 틀린 걸 믿음)는 여전히 유효합니다
  - 대안: 인식 결과를 **"기계가 이렇게 들었다"** 형태로 표면화하고 원문 입력을 병기
    → "잘못 믿는" 문제가 표면적 표시로 사라집니다

## 7. 화면과 사용자 경험

### 모드

현재는 모드가 하나뿐입니다(자유 형식 튜터 대화). 제안:

- **자유 대화** — 기본값. 이게 메인
- **복습** — 지난 오류와 표현을 다시 보는 곳

상세한 상황 롤플레이가 필요하다면 `/chat`이 이미 그 역할을 합니다.
`/english`가 또 다른 채팅으로 남으면 아무도 쓰지 않습니다.
이 기능의 정체성은 **자기 규율된 연습 + 학습 기록**입니다.

### 언어 규칙 (구현 시 지켜야 함)

- **UI와 튜터 설명: 한국어**
- **예문·연습·비즈니스 표현: 영어**

튜터가 한국어로 계속 설명하면 그건 프리 토킹 훈련이 아니라 한국어 수업입니다.
설명은 한국어로 하되, **영어 예문 자체는 언제나 자연스러운 영어**로.

### 세션 흐름 (4단)

1. **시작** — 오늘 하고 싶은 것 / 이번 주 상황 하나만 고릅니다.
   실력 조사를 하거나 레벨을 고르는 화면을 넣지 않습니다. 이미 아는 걸 다시 묻지 않습니다
2. **대화** — 주제 안에서 자유롭게. 주제와 상황만이 틀입니다
3. **마무리** — 스크롤 가능한 요약:
   오늘의 표현 / 내가 틀린 것 / 다음에 연습할 것
4. *(다음 세션)* — 첫 대화에서 지난번 표현을 되살립니다

### 세부 원칙

- 대화 중 화면에 튜터 설명이 길게 붙지 않게 합니다. 간결하게
- 모든 예문에 번역을 다 붙이면 학습 신호가 흐려집니다. **직접 말해보는 순간의 번역만** 필요합니다
- 말하기 연습을 시작하기 전에 교정으로 흐름을 끊지 않습니다
- 오류는 AI 응답처럼 말풍선에 섞지 말고 별도 영역에 (기존 규칙 `07-rules.md` 3)

## 8. 기존 구현과의 관계

> **이 절의 성격**: "갈아엎는다"는 **제안**입니다.
> 사용자는 확신이 없다며 그렇게 코멘트해 두었습니다.
> 실제 범위는 구현자가 사용자와 확정할 것.

### 버릴 것 (제안)

- `Phase` enum (`intro` / `examples` / `roleplay` / `output` / `summary`)과 단계 진행 개념.
  대화 흐름을 매번 같은 모양으로 잘라 놓는 구조입니다
- `StepType`의 2분법 (`example` / `output_prompt`).
  학습 형식은 예문과 연습 둘만 있는 게 아닙니다
- 단계 진행을 프롬프트로 부탁하는 방식.
  형식(jsonMode)은 강제할 수 있어도 **순서와 양**은 강제되지 않습니다
- 화면에서의 학습자 수준·목표 선택 UI

### 남길 것 (재사용 가치 있음)

- `lib/lesson.ts`의 **계약 분리 구조** — 계약(타입·파롬프트·파서)과 화면을 나눈 판단은 그대로 유효
- **파서가 절대 던지지 않는** 원칙. 파싱 실패로 500을 띄우는 건 도움되지 않는 화면입니다
- 턴을 `meta`에 통째로 저장해 복원하는 구조 (`D-016`). 예문·번역이 구조를 잃지 않게 합니다
- `turnToHistoryText`의 압축 원칙 — 화면 전용 메시지를 다음 호출에 통째로 넣지 않는 것
- 컨텍스트 토큰 예산 (`D-014`). 영어 대화는 반복이 많아 예산을 빨리 채웁니다
- `SpeakButton` (Web Speech, `D-017`) — 키도 비용도 의존성도 없다는 판단은 유효합니다
- 화면 저장 후 복원 (`metaToTurn`) 패턴

### 판단의 방향

갈아엎는다면 **기존 코드를 수정하지 말고 새로 만드는 쪽**을 권합니다.
현재 구조를 손보면 중간 상태가 오래 남고, 어차피 계약(프롬프트·응답 형태)이
처음부터 달라지므로 수정 이력이 산이 됩니다.

## 9. 구현 순서 (방향 제시)

1. 학습 기록 데이터 모델을 먼저 정합니다. 화면보다 이게 먼저입니다.
   나중에 붙이면 기존 대화 데이터와 새 스키마가 어긋납니다
2. 대화 루프와 프롬프트 계약 (단계·모드는 과감하게 줄입니다)
3. 대화 화면
4. 마무리 요약 + 오류 기록
5. 다음 세션에 그 기록을 되살리는 경로
6. 복습 화면
7. 발음 반복 (최소대조 / 섀도잉)
8. 음성 입력 — 별개 결정 (브라우저 제약이 있음)

4~5번이 이 기능의 존재 이유입니다. 1~3번까지만 하고 멈추면 그냥 채팅입니다.

## 10. 구현 전에 사용자와 합의할 것

이 문서에 두지 않은 것들입니다. 코드를 쓰기 전에 논의가 필요합니다.

- **시스템 프롬프트 문구** — 위 원칙들을 어떤 문장으로 넣을지. 규칙 문서(`D-015`)대로
  형식 강제는 계층적으로 하되, 우선순위 충돌 시 무엇이 이기는지 미리 정해야 합니다
- **오류 분류 체계** — 몇 개로 나누고, 누가 정하는지(모델이 매기나, 코드 사전으로 강제하나)
- **반복 주기 정책** — 오류를 언제 다시 꺼낼지. 계측 기반이 되기 전까지는 휴리스틱
- **비즈니스 상황 목록** — 사용자가 실제로 만날 상황을 먼저 묻고 그걸 목록으로
- **기존 영어 대화 데이터의 처리** — 마이그레이션, 폐기, 목록에서 숨길지
- **provider·모델별 품질 편차** — 프리 토킹은 응답 길이가 길어 지연이 체감됩니다.
  튜터 품질이 provider마다 다르면 학습 경험이 매번 달라집니다. 어느 수준을 기준으로 삼을지
- **평가 방법** — 프롬프트를 바꿨을 때 좋았는지 판단할 기준. 지금은 없으므로
  아무것도 측정하지 않은 상태입니다

---

## 11. 하지 않는 것 (기록용)

- 문법 커리큘럼 / 레벨별 코스
- 시험 대비, 채점, 점수, 배지
- 스피킹 AI 평가 ("발음 87점") — 신뢰할 수 없는 수치를 화면에 올리는 것은 해롭습니다
- 자동 발음 판정 — 신뢰도 부족. 대신 반복으로만 접근합니다
- 학습 통계 대시보드 — 데이터가 쌓이는 데 시간이 걸립니다. 쌓인 뒤 판단합니다
