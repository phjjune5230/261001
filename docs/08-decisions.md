# 08. 결정 기록 (Decisions)

## 이 문서의 목적

"왜 이렇게 됐는가"를 나중에 되짚기 위한 문서입니다.
코드만 보면 **무엇**을 한 것인지는 보이지만, **왜**를 담은 곳은 여기뿐입니다.

새로 내린 결정은 코드를 고치기 **전에** 여기에 먼저 남깁니다.
(`docs/07-rules.md` 4번 규칙)

각 항목 형식:

- **기록일**: 이 결정이 문서에 남은 날짜
- **상황**: 어떤 문제가 있었는가
- **결정**: 무엇을 정했는가
- **근거**: 왜 이쪽인가
- **대안 기각**: 왜 다른 쪽은 안 됐는가

## D-001. Anthropic(Claude) provider 제외

- **기록일**: 2026-10-01
- **상황**: 초기 설계에 Anthropic provider와 `@anthropic-ai/sdk`가 포함돼 있었으나 실제로 쓰지 않게 되었다.
- **결정**: `lib/llm.ts`의 `ALL_PROVIDERS`, `PROVIDER_CONFIG`, API 호출 분기에서 완전히 제거한다. OpenRouter 목록의 `anthropic/claude-*` 계열 model ID도 함께 뺀다.
- **근거**: 사용하지 않는 provider는 화면에 고를 수 있게 두면서도 실패만 일으킨다. 기본 provider가 아니면 아무도 못 고르지만, 목록에 있으면 "왜 이건 안 되지?" 하는 혼선을 만든다.
- **대안 기각**: 나중에 다시 넣을 수도 있으니 남겨두는 쪽 — 제외했다가 추가하는 게 코드 한 줄보다 싸다.

## D-002. provider를 3개로 한정

- **기록일**: 2026-10-01
- **상황**: provider가 늘어날수록 설정과 실패 경우가 함께 늘어난다.
- **결정**: `openrouter`, `groq`, `gemini` 3개만 지원한다. `ALL_PROVIDERS`가 단일 기준이다.
- **근거**: provider 선택은 사용자가 직접 하므로, "쓰지 않을 provider를 고를 수 있는 상태"를 만들지 않는 것이 목표다. `Record<Provider, ...>` 타입이라 provider를 늘리면 컴파일 에러로 잡힌다.
- **대안 기각**: 자동 폴백(provider가 죽으면 다음 걸로) — Phase 1의 목표가 "어떤 provider가 어떤 모델을 쓰는지 사용자가 직접 아는 것"이다. 자동 폴백은 그 목표를 흐린다.

## D-003. 모델 설정을 `lib/models.ts` 한 곳에 통합

- **기록일**: 2026-10-01
- **상황**: model ID가 `llm.ts`, `chat/page.tsx`, 문서 세 곳에 흩어져 있었다. 하나 고치면 한 곳만 고쳐지는 상태였다.
- **결정**: `MODELS`, `DEFAULT_PROVIDER`, `defaultModelFor()`를 `lib/models.ts`로 모은다. `lib/llm.ts`는 이 파일을 참조만 한다.
- **근거**: 사용자가 직접 모델을 관리한다. 고칠 곳이 한 군데여야 새 모델을 즉시 추가할 수 있다. 각 provider 목록의 첫 항목이 그 provider의 기본 모델이 된다.
- **대안 기각**: `llm.ts`에 그대로 두기 — 라우팅과 목록 설정이 한 파일에 섞여 어느 게 설정인지 분리가 안 된다. `models.ts`가 `llm.ts`를 `import type`로만 참조하므로 순환 의존도 없다.

## D-004. 스트리밍 미도입

- **기록일**: 2026-10-01
- **상황**: 설계 문서에는 스트리밍 응답이 In Scope로 되어 있었으나 구현되지 않았다.
- **결정**: Phase 1은 전체 응답을 받은 뒤 렌더링한다. `/api/chat`은 `NextResponse.json`으로 JSON을 반환한다.
- **근거**: 스트리밍은 UX 개선이지 기능이 아니다. 어느 provider로 어느 모델을 쓰는지 확인하는 게 지금 목적이라, 응답이 도착하면 그걸로 충분하다.
- **대안 기각**: 바로 도입 — provider마다 스트리밍 응답 형식이 달라 정규화가 필요하고, 그 전에 확인해야 할 provider 상태가 아직 불안정하다.
- **재검토 조건**: 응답이 체감될 만큼 길어지면(영어 학습 기능의 롤플레이 등) 다시 논의한다.

## D-005. 재시도에서 할당량 초과 제외

- **기록일**: 2026-10-01
- **상황**: Gemini가 503을 던질 때 재시도를 넣었더니, 할당량(429)을 포함한 모든 오류를 재시도했다. 재시도해봐야 소용없는데 한도만 빨리 소진됐다.
- **결정**: `TRANSIENT`(5xx·네트워크만)과 `NON_RETRYABLE`(quota·billing·api key·invalid)로 분리한다. 두 조건을 모두 만족할 때만 재시도한다.
- **근거**: Gemini free tier는 모델당 일 20회 한도다. 429는 "45초 후 재시도하라"고 안내하지만 실제 제약은 일별 한도라 재시도가 무의미하다.
- **대안 기각**: 재시도 횟수를 늘리기 — 실패를 늦출 뿐 크레딧을 더 소모한다.

## D-006. gemini 기본 모델을 Flash Lite로

- **기록일**: 2026-10-01
- **상황**: gemini 기본 모델이 일 20회 한도 모델이라 검증하는 동안 곧바로 한도가 소진됐다.
- **결정**: gemini 기본 모델을 Flash Lite(일 500회)로 둔다.
- **근거**: 개인 사용 빈도에서는 500회가 실용적인 상한이다. 다른 모델로 바꾸면 일 20~50회로 떨어진다.
- **대안 기각**: 유료 모델 — 쓰지 않는 날에도 비용이 생긴다.
- **재검토 조건**: 사용량이 일 500회를 넘어가면 그때 유료 전환을 검토한다.

## D-007. 접근 보호는 6자리 PIN (화면 + API 헤더)

- **기록일**: 2026-10-01
- **상황**: `/api/chat`에 인증이 전혀 없었다. 공개 URL로 올리면 URL을 아는 사람이 그대로 POST를 보내 사용자의 API 크레딧을 소모할 수 있었다. 화면도 `/chat`이 주소로 직접 열려 홈 화면에만 잠그는 방식으로는 효과가 없었다.
- **결정**:
  1. `APP_PIN` / `APP_TOKEN`을 `.env.local`에만 둔다. **`NEXT_PUBLIC_` 접두사를 절대 붙이지 않는다.**
  2. `POST /api/auth`가 PIN을 검증하고 `APP_TOKEN`을 발급한다.
  3. 클라이언트는 **PIN이 아니라 토큰**을 `sessionStorage`에 보관한다.
  4. `POST /api/chat`은 `x-app-token` 헤더가 없거나 틀리면 401을 반환한다 — 본문 파싱보다 먼저 검사한다.
  5. 모든 화면 라우트는 `app/layout.tsx`의 `AuthGate`를 거친다.
- **근거**: 사용자가 *"아직은 이정도로 충분함. 그렇게까지 보호할껀 아님"*이라고 명시했다. 목표는 "URL만 알면 끝"인 상태를 막는 것이지 실제 보안이 아니다. 접두사를 붙이지 않아야 PIN이 JS 번들에 평문으로 실리지 않는다. PIN과 토큰을 분리한 이유는 PIN 자체가 sessionStorage에 남지 않게 하려는 것이다.
- **대안 기각**:
  - **강한 인증(서버 세션 + 쿠키)** — 요구 수준을 넘어선다.
  - **Next 16의 `proxy.ts`로 서버에서 막기** — 검증해 보니 이 Next 버전(`16.2.6`)에 실제로 존재한다(`node_modules/next/dist/lib/constants.js`의 `PROXY_FILENAME = 'proxy'`). 서버에서 막으면 인증 없는 요청에 대해 보호된 HTML을 아예 생성·전송하지 않아 더 깨끗하다. **채택하지 않은 이유**: 이 앱의 페이지 HTML에는 비밀 정보가 없고, 실제로 보호해야 할 `/api/chat`은 현재 방식으로도 완전히 막힌다. 실패 리스크를 더하는 대신 얻는 것이 없어 보인다. **UI를 민감한 데이터로 넓히는 시점에 다시 검토할 것.**
  - **홈 화면에만 잠그기** — `/chat` 주소를 직접 치면 통과한다. 효과가 없다.
- **알려진 한계 (의도된 것)**: 토큰이 sessionStorage에 있으므로 개발자도구로 읽을 수 있다. 또한 시도 제한이 없어 6자리 조합 100만 개는 전부 시도할 수 있다. 즉 **"URL만 아는 사람"은 막지만 "집요한 사람"은 막지 못한다.** 사용자가 정한 수준이 여기까지다.

## D-008. 이전 프로젝트는 컨셉만 참조, 코드 이식 금지

- **기록일**: 2026-10-01
- **상황**: 이전 스터디 프로젝트 `C:\june\old`가 존재한다. 사용자가 *"컨셉만 따오고 새로 설계한다고 생각하면 돼"*라고 명시했다.
- **결정**: OLD의 **아이디어만** 참조한다. 파일을 복사하거나 이식하지 않는다.
- **근거**: OLD는 공부·검증용으로 설계·관리 과정을 고려하지 않고 만들어졌다. 이번은 실 사용 목적이라 처음부터 다시 설계한다. 겉모습만 물려받으면 OLD의 구조적 결함이 그대로 따라온다.
- **대안 기각**: 점진적 이전 — 어느 정도까지 이식할지 경계가 흐려지고, 중간에 되돌리기 어렵다.
- **참고**: OLD가 이미 해낸 것(영어 커리큘럼, Text-to-SQL, 코드봇, 에러 카운트 자동 폴백)은 Phase 2 이후 설계할 때 컨셉으로 유용하다. 다만 규칙 문서에는 OLD 파일명만 인용하고, 구현을 권유하지 않는다.

## D-009. 버전 관리를 Markdown으로 먼저, git 태그로 대응

- **기록일**: 2026-10-01
- **상황**: git이 설치돼 있지 않고 이 폴더도 저장소가 아니다. 그런데 설계 문서에는 "기능 단위로 커밋 작성"이라는 규칙이 있었다 — 지킬 수 없는 규칙이 적혀 있는 셈이었다.
- **결정**: `package.json`의 `version`을 기준으로 SemVer를 쓰고, `docs/09-changelog.md`에 이력을 남긴다. git을 설치한 뒤에는 같은 문자열로 태그를 붙인다(`v0.2.0`).
- **근거**: 규칙을 지킬 수 없는 상태에서 규칙만 적어두는 것은 규칙이 아니라Wish다. Markdown부터 시작하면 지금도 규칙을 지킬 수 있다.
- **대안 기각**: git을 먼저 설치 — 버전 관리 자체를 미루게 된다.

| 구분 | 기준 | 예 |
|------|------|-----|
| patch | 버그 수정, 문서 정정, 의존성 변경 | 죽은 model ID 교체, 문서 오류 |
| minor | 기능 추가, Phase 진행 | 접근 게이트, 영어 화면 |
| major | 계약·스키마 등 호환성이 깨지는 변경 | `/api/chat` 응답 형식 변경 |

**규칙**: 이력 항목과 git 태그는 같은 커밋에서 만들어진다.

## D-010. `next/font/google`로 폰트 로드

- **기록일**: 2026-10-01
- **상황**: `app/layout.tsx`에서 Google Fonts를 `<link>`로 직접 호출하고 있었다.
- **결정**: `next/font/google`의 `DM_Mono`, `Syne`을 쓰고 CSS 변수(`--font-dm-mono`, `--font-syne`)로 노출한다.
- **근거**: 빌드 시점에 폰트를 내려받아 self-host + preload한다. 페이지마다 다시 로드되지 않고 FOUT도 없다.
- **주의**: 이 방식을 쓰면 `fontFamily: "'Syne'"` 같은 리터럴 이름은 쓸 수 없다. 반드시 CSS 변수를 쓴다. (기존 인라인 스타일이 전부 이 문제로 깨졌었다)

## D-011. UI 기본 provider는 `groq`

- **기록일**: 2026-10-01
- **상황**: OpenRouter 키가 "Key limit exceeded" 상태여서 기본값으로 쓰면 첫 화면이 실패한다.
- **결정**: `DEFAULT_PROVIDER = 'groq'`.
- **근거**: 실제 호출로 응답을 확인한 provider만 기본값으로 둔다.
- **대안 기각**: OpenRouter를 기본으로 두고 크레딧 충전을 기다리기 — 그동안 앱이 안 된다.
- **재검토 조건**: OpenRouter 크레딧을 충전하면 기본값을 되돌리고 이 항목을 여기서 지운다. **이건 취향이 아니라 과금 상태를 우회한 임시 조치다.**

## D-012. 모델 "직접 입력…" 우회로

- **기록일**: 2026-10-01
- **상황**: model ID가 빠르게 폐기된다. 목록에 없는 모델을 쓰려면 매번 코드를 고쳐야 했다.
- **결정**: 채팅 화면의 모델 선택에 "직접 입력…" 항목을 둔다. ID만 타이핑하면 그대로 쓴다.
- **근거**: D-003의 "고칠 곳은 한 군데"를 화면에서도 지킨다. 코드 수정 없이 새 모델을 즉시 시험할 수 있다.
- **참고**: 이 우회로가 model ID가 썩는 문제를 고치는 건 아니다. 목록에 없는 ID가 깨지면 바로 드러난다.

## D-013. 잠금 화면은 오버레이로 덮는다

- **기록일**: 2026-10-01
- **상황**: 잠금 화면을 넣는 첫 구현이 토큰 확인 전까지 렌더를 미루는 방식이었다. 그러면 첫 페인트에 빈 화면이 보이고, `useEffect` 안에서 `setState`를 불러 React가 경고했다(`react-hooks/set-state-in-effect`).
- **결정**: 자식은 항상 렌더하고, 잠을 때만 잠금 화면을 `fixed` 오버레이로 덮는다. 토큰은 `useSyncExternalStore`로 읽는다.
- **근거**: D-007에서 sessionStorage를 선택했기 때문에 보호된 페이지 HTML은 어차피 이미 전송된다. 따라서 "그리지 않는다"는 이득이 없고 깜빡임만 남는다. sessionStorage는 React 밖의 저장소이므로 `useSyncExternalStore`가 그 경로의 정식 해법이다.
- **주의**: D-007에서 proxy.ts(서버 게이트)로 전환한다면 이 결정은 함께 뒤집어야 한다. 서버에서 막으면 보호된 HTML을 애초로 보내지 않으므로 오버레이 방식이 불필요해진다.

## D-014. 컨텍스트는 턴 수가 아니라 토큰 예산으로 자른다

- **기록일**: 2026-10-01
- **상황**: 채팅이 길어지면 매 턴 대화 전체를 그대로 보냈고, 결국 provider가 거절했다. 사용자가 지적한 그대로였다 — "대화 막 50개 100개 이렇게 되면 토큰 녹자나."
- **결정**: `lib/context.ts`의 `keepRecentMessages()`로 최근만 남긴다. 첫 메시지가 `system`이면 절대 버리지 않는다.
- **근거**: 턴 수는 나쁜 기준이다. 코드 블록이 잔뜩인 턴이 수천 토큰이고 "ㅇㅇ"가 몇 토큰인지 알 수 없다. 예외는 시스템 프롬프트 하나뿐 — 지시문이 사라지면 이후 응답의 의미가 통째로 바뀌므로 어떤 경우에도 지킨다.
- **대안 기각**: "20턴마다 요약" — 흔히 말되는 방식이지만 요약 자체가 또 하나의 호출이고 비용이 든다. Turn 수는 기준이 되지 못하니 순서도 근거가 약하다. 요약은 별도 결정(D-016)으로 미룬다.

### 예산 상수는 왜 6,000인가

**모델의 컨텍스트 창이 아니라 분당 토큰(TPM) 한도에 맞춘 값이다.**

2026-10-01 실측으로 확인했다. 한글 3,000자 × 41턴짜리 대화에서 처음 12,000 예산으로 잘랐더니
groq가 `openai/gpt-oss-120b`에 대해 아래와 같이 거절했다.

```
Request too large ... on tokens per minute (TPM): Limit 8000, Requested 46197
```

모델의 컨텍스트 창은 128k인데 여기서 막힌다. 6,000으로 내린 근거는 이것이다.
출력(`max_tokens` 1024) 자리도 남겨 둔다.

**이 상수는 자주 바뀌는 값이다.** provider나 모델을 바꾸면 먼저 그 계정의 실제 TPM 한도를 확인하고
`docs/09-changelog.md`의 정기 점검에 적을 것.

### 한글은 4글자가 1토큰이 아니다

위 사고의 진짜 원인은 예산 크기가 아니라 **추정기가 틀렸다**는 점이었다.
"문자 수 ÷ 4"는 영문에서만 성립한다. 한글은 글자 1개가 거의 1토큰이다.

처음 재었을 때 41턴을 12,000토큰으로 판단해 잘라 보냈지만 실제 요청은 46,197이었다.
과소평가 3.8배. 예산 가드가 조용히 무력화된 셈이다.

`estimateTokens()`는 한글·한자·일본어(코드포인트 범위로 판별)를 따로 세고 나머지를 4로 나눈다.
고친 뒤 한글 3,003자 → 3,020토큰으로, provider가 세는 값과 거의 정확히 일치했다.

## D-015. 영어 기능은 jsonMode로 구조를 강제한다

- **기록일**: 2026-10-01
- **상황**: 영어 학습은 한 줄 답변이면 안 된다. 예문·번역·연습문장이 각각 다른 화면 요소다. 모델에게 "이렇게 답해"라고 프롬프트로만 부탁하면 형식이 매번 흔들린다.
- **결정**: `callLLM()`에 `jsonMode` 옵션을 추가한다. OpenAI 호환 엔드포인트는 `response_format: { type: 'json_object' }`, Gemini는 `generationConfig.responseMimeType`. 영어 라우트는 이걸 켠다.
- **근거**: 프롬프트로 부탁하는 것과 파서가 붙는 것은 신뢰성이 다르다. 파싱에 실패하면 UI가 깨지는 구조라 형식을 보장하는 편이 낫다.
- **주의**: OpenAI 호환 엔드포인트는 JSON 모드일 때 프롬프트에 `json`이라는 단어가 없으면 400을 낸다. `LESSON_SYSTEM_PROMPT`에 이미 들어 있다. 프롬프트를 고칠 때 이 단어를 지우면 조용히 실패한다.
- **대안 기각**: 파싱 실패를 무시하고 원문을 그대로 말풍선에 찍기 — 사용자는 왜 예문이 글자 `{`로 시작하는지 모른다. `parseLessonResponse`는 절대 던지지 않고, 실패하면 `steps: []`로 통과시킨다.

## D-016. 화면 전용 메시지는 다음 호출에 넣지 않는다

- **기록일**: 2026-10-01
- **상황**: OLD에는 이 규칙이 `ChatWindow.tsx` 한 줄로 들어 있었다. 영어 기능으로 옮기면서 한 줄로는 부족해졌다 — 예문이 여러 개 쌓이니까.
- **결정**: 영어 화면은 예문·번역을 **API로 보내지 않는다.** `turnToHistoryText()`가 모델이 "무엇을 이미 말했는지" 알 수 있을 만큼만 압축해서 다음 턴의 assistant 메시지로 넣는다.
- **근거**: 구조를 통째로 직렬화하면 JSON 키가 매번 반복되고, 메시지가 "예문 단가"가 아니라 "_JSON 키 단가_"로 토큰을 먹는다. 실측: 예문 3개 + 다음 턴 요청이 **112토큰**이었다.
- **이건 OLD에서 컨셉만 가져온 것**이다 (D-008 — 코드는 이식하지 않는다). `historyForAPI` 한 줄을 통째로 복사하지 않고, 다단계 말풍선을 처리하도록 다시 설계했다.

### 아직 하지 않는 것

- **요약 압축(compaction)**: 오래된 내용을 요약으로 대체. 요약 호출 비용, 요약이 잘못되면 이후 대화가 오염되는 문제, 언제 할지 판단 기준이 전부 미해결. D-014의 "버리기"만 해두고 미룬다.
- **프리픽스 캐싱**: provider는 입력의 *앞부분*을 해시한다. 그래서 "변하지 않는 건 앞에, 변하는 건 뒤에"가 원리다. 시스템 프롬프트가 이미 맨 앞에 붙어 있어 조건은 갖춰졌지만, 실제 절약 효과를 provider별로 계측해 보기 전에는 "이득이 있다"고 단정하지 않겠다.

## D-017. 발음은 Web Speech API로 읽는다

- **기록일**: 2026-10-01
- **상황**: OLD는 예문마다 🔊 버튼을 두었다. 음성 기능이 영어 학습의 핵심인데, TTS를 넣으려면 API 키와 과금이 따라온다.
- **결정**: 브라우저 내장 `speechSynthesis`를 쓴다. 키도, 비용도, 의존성도 없다.
- **근거**: 읽는 것까지만 하면 브라우저가 충분하다. 개인 학습용으로는 합성 음질보다 **읽을 수 있는지가** 먼저다. 또 앱은 거의 항상 브라우저에서 도는 personal 앱이라 서버 경유가 필요 없다.
- **한계 (기재)**: 음성이 OS·브라우저마다 다르다. 크로스브라우저·고품질을 원한다면 서버 TTS로 바꿔야 하고, 그때는 키와 비용이 생긴다.
- **대안 기각**: 서버 TTS — 첫 학습도 전에 키·과금·캐시를 다 얹어야 한다. "나중에 필요하면 바꿀 수 있다"가 이 선택의 근거다.
- **보류**: 음성 **입력**(STT)은 넣지 않았다. `SpeechRecognition`은 Chrome 한정이고 오인식이 잦아서, 틀린 영어를 학습자가 "틀렸다고 믿고 따라 하는" 상황이 더 나쁘다.

## D-018. 대화 저장은 Supabase Postgres에 한다

- **기록일**: 2026-10-01
- **상황**: 앱이 `localhost` 전용이었다. 그런데 사용자가 **URL로 어디서나 접속**하려 했고, 지금 구조로는 대화가 `useState`에만 있어 새로고침하면 전부 사라진다. 프로바이더가 과금형(OpenRouter·Groq)이라 사라진 대화는 곧 사라진 지출이다.
- **결정**: Supabase에 `conversations` + `messages` 두 테이블로 저장한다. chat과 english는 같은 스키마를 쓰고 `kind`로만 구분한다.
- **근거**: Postgres라 나중에 검색·집계 질의가 가능하고, 인증(auth)이 내장이라 사용자 분리까지 같은 곳에서 끝난다. 무료 티어가 이 규모엔 넉넉하다.
- **대안 기각**:
  - *localStorage* — 서버 비용 0이지만 브라우저를 지우면 날아가고 기기 간 이동이 안 된다. "URL로 접속"이라는 목표 자체와 충돌.
  - *Firebase/Firestore* — NoSQL이라 서버 라우트에서 다루기 번거롭고, 읽기 비용이 예측하기 어렵다는 평이 있다.
  - *별도 테이블 두 개(chat/english)* — 영어 턴은 `steps[]`를 갖고 chat은 그렇지 않다. 하지만 **저장 형식의 차이는 애플리케이션이 아는 문제**이지 스키마가 알 필요는 없다. `meta jsonb` 하나로 충분하므로 분리하지 않는다.
- **위험 (기재)**: 개인 프로젝트에서 데이터가 새는 경로는 거의 **RLS 설정 실수**다. `supabase/schema.sql`에서 `create table`과 `enable row level security`를 한 블록에 묶은 이유가 이것이다. 나중에 켜려면 그 사이 창이 생긴다.

## D-019. 사용자 인증은 Supabase Auth에 맡긴다

> **[D-022로 부분 무효]** 아래 결정의 "브라우저가 anon 키로 직접 붙는다"는 부분은
> 2026-10-01에 뒤집혔습니다. 접근을 서버로 옮겼습니다.
> D-019가 붙인 D-007(6자리 PIN, `x-app-token`)은 **그대로 유효합니다.**

- **기록일**: 2026-10-01
- **상황**: 사용자가 앱을 **일부 사람에게 공유**하기로 했다. 대화가 사람마다 섞이면 안 된다.
- **결정**: Supabase Auth(로그인)를 쓴다. 인증 토큰이 곧 `auth.uid()`가 되고, RLS가 그걸로 걸러낸다. **사용자 ID를 애플리케이션에서 만들지 않는다.**
- **근거**: RLS 정책이 `auth.uid()`와 `user_id`를 비교하는 한 줄로 끝난다. 애플리케이션이 "누가 로그인했는지"를 판정하는 코드를 쓰지 않아도 데이터가 분리된다 — **DB가 강제하므로 클라이언트가 속여도 못 넘는다.**
- **대안 기각**: *사람마다 PIN을 발급하고 DB에 PIN을 키로 저장* — 로그인 폼을 안 만들어도 된다고 tempting해 보이지만, **자기가 아는 ID로 다른 사람 대화를 조회할 수 있는** 구조가 된다. 진짜 분리가 아닙니다. 지금의 6자리 `APP_PIN`은 이 용도가 아니라 앱 문을 여는 로컬 잠금으로만 씁니다.
- **변하지 않는 것 (중요)**: D-007의 `APP_TOKEN`/`x-app-token`은 **그대로 둡니다.** 이건 화면 잠금이 아니라 **지갑 보호**입니다. 로그인 인증이 생겨도 `/api/chat`에 토큰 검사를 빼면, 앱을 열지 않고 `curl` 한 줄로 API 키 크레딧을 태울 수 있습니다. 두 인증은 목적이 다릅니다.
- **한계 (기재)**: "일부 사람에게 공유하고 URL이 안 퍼진다"는 전제 위에 서 있습니다. 사람이 늘어 암호 관리(재설정, 강제 탈퇴, 공유 해제) 문제가 생깁니다. 그때는 profiles 테이블과 관리 화면이 필요합니다.

## D-020. 배포는 Vercel로 한다

- **기록일**: 2026-10-01
- **상황**: "어디서나 URL로 접속" 요구가 들어왔고, 검토된 적이 없었다.
- **결정**: Vercel Hobby 플랜. 환경 변수는 7개(`APP_PIN`, `APP_TOKEN`, provider 키 3개, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`)를 Vercel 대시보드에 등록한다. **모두 `NEXT_PUBLIC_` 접두사 없이.** (D-022에서 anon 키가 `service_role`로 교체됨)
- **근거**: Next.js를 만든 곳이라 설정이 0이고, GitHub 연동이 기본 제공된다. Hobby 티어의 대역폭(100GB)으로 개인 사용은 충분하다.
- **대안 기각**: *Netlify* — Next.js App Router 지원이 약하다. *Cloudflare Pages* — 싸지만 Next.js SSR 셋업이 성가시다. *Railway/Render* — 서버를 직접 운영해야 해 관리 비용이 발생한다. *집 PC 직접* — 공인 IP·포트 개방이 필요하고 집 주소를 노출하게 된다.
- **보안 (기재)**: **환경 변수 값은 사용자가 직접 등록하며 에이전트를 거치지 않는다.** Supabase 키와 provider 키가 대화 기록에 불필요하게 노출될 수 있습니다. D-022 이후 보안 경계는 RLS가 아니라 **우리 서버의 `x-app-token` 검사 하나**입니다. `SUPABASE_SERVICE_ROLE_KEY`에는 접두사를 절대 붙이지 마세요 — 붙는 순간 RLS 우회 키가 JS 번들에 평문으로 실립니다.
- **남는 위험**: Hobby 플랜의 **함수 메모리 512MB 제한**, 그리고 Vercel 리전에서의 provider **TPM 한도**는 로컬과 다를 수 있습니다.
- **배포 후 확인 (2026-10-01)**: `https://261001-zeta.vercel.app`에 실제로 배포했고, groq 호출이 성공했습니다. 즉 6,000 예산이 Vercel 리전에서도 거절되지 않습니다. **단, 한 번 성공은 한도가 같다는 증명이 아닙니다** — 긴 대화 여러 턴을 돌려보고 여전히 통과하는지 나중에 확인하세요. 함수는 라우트 하나씩이라 512MB 제한에 걸릴 가능성이 낮습니다.



## D-021. 로그인은 아이디 + 비밀번호 (내부적으로는 이메일)

> **[D-022로 완전 무효]** 로그인이 없어졌습니다. 아래는 왜 그 로그인이 애초에
> 필요했는지를 설명하는 기록으로만 남깁니다. 특히 `example.com` 변환과
> "Confirm email" 끄기 설정은 **지금이면 하지 마세요.** 하지 않아도 됩니다.

- **기록일**: 2026-10-01
- **상황**: 로그인 화면이 처음엔 이메일 입력으로 나왔고, 사용자가 "아이디/비번으로 가자"고 했습니다.
- **결정**: 화면은 **아이디 + 비밀번호**만 받는다. 내부에서 `아이디@example.com`으로 바꿔 Supabase에 넘긴다.
- **근거**: Supabase Auth에 "아이디"라는 종류가 **없습니다.** 신원의 유일한 기준이 이메일이고(`auth.users`의 고유 키), 비밀번호 찾기도 전제하고 설계된 시스템입니다. 그런데 **우리가 아는 건 id(uuid)뿐**입니다. RLS 정책은 `auth.uid()`로만 동작하고 어떤 정책도 이메일을 참조하지 않습니다. 그러므로 이메일을 쓰든 말든 보안 경계는 전혀 달라지지 않습니다.
- **왜 `example.com`인가**: 사용자에게 메일을 보낼 일이 없는데 실제 주소를 넣으면 그 주소가 새어 나올 수 있습니다. `example.com`은 RFC 2606이 **문서용으로 예약**한 도메인이라 누구도 등록하거나 메일을 받을 수 없습니다. 이미지 도메인은 실수로 수신 가능한 주소가 될 여지가 남습니다.
- **대안 기각**: *Supabase 네이티브 username 지원* — 대시보드 설정에 의존하는 방식이라 프로젝트 설정이 바뀌면 로그인이 통째로 깨집니다. 드롭다운 하나로 통제하는 이 설계가 더 안전합니다. 나중에 네이티브가 확실해지면 이 장치만 걷어내면 됩니다.
- **대가 (기재)**: **비밀번호 찾기를 이메일로 할 수 없습니다.** 잊어버리면 Supabase 대시보드 SQL에서 직접 지워야 합니다. 쓰는 사람이 몇 명이고 직접 통제하므로 감수합니다. 사람이 늘어나면 이 결정의 대가가 문제가 됩니다.
- **필수 사전 설정 (중요)**: Supabase 대시보드 → **Authentication → Sign In Providers → Email → "Confirm email"을 꺼야 합니다.** 켜져 있으면 가입 시 인증 링크를 보내는데, 보낼 주소가 없습니다. 계정이 만들어지지만 **절대 로그인할 수 없는** 상태가 됩니다. 끄지 않으면 가입 자체가 막힙니다.

## D-022. 대화를 브라우저에서 서버로 옮기고, 로그인을 없앤다

- **기록일**: 2026-10-01
- **상황**: D-019로 Supabase Auth 로그인을 만들었고 D-021로 아이디/비밀번호로 바꿨습니다.
  그런데 이 앱은 **한 사람이 쓰는 앱**입니다. 화면에 로그인 폼이 올라오는 순간
  판단할 수 있는 사실이 하나였습니다 — 이 구조는 사람 여러 명을 전제한 구조입니다.
- **사용자 결정**: "나만 쓰는거고, db 저장은 필요하고, url 필요하고."
- **결정**: Supabase Auth를 전부 제거합니다. 대화가 브라우저에서 우리 서버로 지나
  `service_role` 키로 저장/조회/삭제됩니다. RLS는 **켜진 채 정책 0개**로 둡니다.
- **왜 RLS 정책이 필요 없어졌나**: D-019가 짠 정책은 전부 `auth.uid()`를 봅니다.
  계정이 없으니 `auth.uid()`는 늘 `null`이고 **어떤 정책도 통과하지 못합니다.**
  즉 그 시점의 RLS는 "누가 이 대화를 볼 수 있나"를 정하는 장치가 아니라
  "아무도 못 본다"를 정하는 장치였습니다. 판단하는 근거가 사라진 규칙입니다.
- **보안은 왜 그대로인가**:
  1. anon은 여전히 아무것도 못 읽습니다. RLS가 켜져 있고 정책이 하나도 없기 때문입니다.
  2. 접근 문이 하나가 됩니다. `/api/chat`도 대화 저장 라우트도 모두 `x-app-token`을 검사합니다.
  3. `service_role`은 `NEXT_PUBLIC_` 접두사가 없어서 클라이언트 번들에 들어가지 않습니다.
- **대안 기각**: *RLS 정책을 열고 브라우저 anon 키로 그대로 읽고 쓰게 둠* —
  이게 겉으로는 가장 간단해 보입니다. 하지만 anon 키는 `NEXT_PUBLIC_` 접두사 때문에
  **JS 번들에 평문으로 실립니다.** URL을 아는 사람은 REST API를 직접 호출해
  대화를 통째로 내려받을 수 있습니다. 대화 저장이 전혀 없던 v0.2.0보다 **더 약해집니다.**
  그래서 서버를 거치기로 했습니다.
- **대가 (기재)**: `service_role`은 RLS를 **완전히 우회**합니다. 라우트에서
  `WHERE` 하나를 빠뜨리면 전체 대화가 나갑니다. D-019가 그 이유로 anon을 택했고,
  지금은 그 논리가 더 이상 성립하지 않아 기꺼이 돌아가는 상황입니다.
  그래서 `app/api/conversations/**` 라우트는 **id나 kind를 절대 브라우저에서
  받지 않고**, 라우트가 조건을 직접 적습니다. "화면에서 안 골라 준 것"을
  필터로 기대하지 마세요.
- **함께 정리한 것**:
  - `conversations.user_id` 열 삭제 (`not null references auth.users(id)`라
    auth.users에 행이 없으면 service_role insert가 외래 키에서 실패합니다)
  - `owns_conversation()` 함수 삭제, 정책 7개 삭제
  - 인덱스를 `(user_id, updated_at)`에서 `(kind, updated_at)`으로 교체
  - `after_message_insert` 트리거에서 `c.user_id = auth.uid()` 조건 제거
  - `SignInForm.tsx` 삭제, `AuthGate.tsx`는 PIN 잠금만 남김
  - anon 키는 클라이언트에서 더 이상 읽지 않습니다 (`NEXT_PUBLIC_` 불필요)
- **이 결정을 뒤집는 조건**: 사람이 둘 이상으로 늘어나면 이 구조는 무너집니다.
  서버가 "누가"를 판정하는 수단이 없기 때문입니다. 그때는 D-019로 돌아가야 하고,
  돌아가는 비용은 `app/api/conversations/**` 라우트 전체에 `user_id` 조건을 다시
  넣는 것이지, `lib/db-server.ts`를 버리는 것이 아닙니다.
- **무효가 된 결정**: D-019의 "브라우저가 anon 키로 직접 붙는다"는 부분,
  D-021 전체(아이디/비밀번호 폼, `example.com` 변환, "Confirm email" 끄기).
  D-019가 붙인 D-007(6자리 PIN, `x-app-token`)은 **그대로 유효합니다.**
  D-019는 로그인이 생겨도 이 둘을 빼지 말라고 명시했는데, 그 경고가 맞았습니다.
